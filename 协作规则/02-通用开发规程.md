# 通用开发规程

> 正式版：2026-09-27（修订）。Agent 按需读取的共同工作方法，唯一维护源，各项目引用它。与项目批准记录不一致时，先核对适用范围和已批准的变更；仍有实质冲突就报告，由用户决定。

## 从哪里读起

- 明确启动真实新项目：先做[新项目启动与最少建档](#project-startup)，再按已授权阶段工作。已有项目改按本规程：做[已有项目接入](#project-adopt)。同一项目新开一个仓库或独立目录树：在建仓库的那张票里按 03 的多仓库约定给它建入口 AGENTS。
- 判断走哪条路线：第 1 节。四阶段：第 2 节。
- 正式功能：第 3 节主线；会话、派工、开工、收工和验证：第 4 节。
- 选 Skill：第 5 节。接手、压缩、整理资料：第 6 节。
- 高风险操作即使没有正式票（恢复、迁移等），也按第 4 节的验证强度做。

## 1. 先按任务和风险选路线

开始任何任务前，先交一行**开工报告**：本次路线、当前关口、本轮结束用户会看到什么。路线变化时重新报告。

| 路线 | 怎么做 | 结束于 |
|---|---|---|
| 问答、诊断、只读审查 | 收集证据，给结论和不确定项；不改项目。 | 回答完毕；要修就说明建议，等修复授权。 |
| 小改动（目标清楚、低风险、易撤回） | 复述目标、边界、验收方式，直接实现并定向验证。 | 交付改动、证据、待查看入口，在施工日志记一行；待人工确认。 |
| 原型、视觉或可行性探索 | 写清要回答的问题，做最小原型，标明模拟部分，在浏览器或目标环境查看。 | 用户决定采用、调整或放弃；采用不等于可直接当生产代码。 |
| 正式功能，或需要多人、多任务接力 | 按第 2、3 节补齐策划、设计、施工依据；已批准部分复用。 | 逐票施工、审查、人工验收，最后整体回归。 |
| 高风险操作或变更 | 在所在路线上加目标核对、授权、故障路径、备份与可恢复性验证。 | 风险验收满足并取得授权；无法安全验证的部分明确报告。 |

高风险清单：真实数据库写入、权限、备份恢复、永久删除、生产部署、密钥、数据迁移。模拟数据和测试环境要明确标出，名字里有“测试”不算标出。

## 新项目启动与最少建档

新项目成立时的一次性建档，不是第五个阶段，也不是每次打开项目的检查。

**触发。** 用户明确要求建立或开始一个真实新项目，且项目目录、当次范围与写入授权能从请求和现有材料确定。在保存首份需要保留的研究、规划资料或产品代码前完成，无需用户另行提醒。当次范围可以只是“先研究使用场景”。位置或授权不清时，只澄清影响当前动作的缺口。

1. **核对已有内容。** 查看适用规则和实际目录，保护已有文件；有合格入口就复用。发现是已有项目，按现行规则接续。
2. **写最少项目规则。** 用 `writing-for-agents`，按 [03 项目规则模板](03-项目规则模板.md) 建根 `AGENTS.md`：真实项目身份、已批准且稳定的原则、特有边界、资料归属和按需路由。模板是检查清单；尚未形成的设计、架构或验证入口标“待确认”。共同流程引用共享规程；当次范围、当前阶段和批准记录留在任务或项目的施工日志（第 6 节），由根规则引用。
3. **接好资料入口。** 根 `README.md` 写简短介绍和人类阅读入口。实际产生资料时按 03 的目录约定建目录和索引，再从根路由接入；目录随内容建立。现有文件保留原位。
4. **写明写回职责，继续。** 在项目规则里写根路由和专题资料各由哪个角色维护，沿用 [04 角色说明](04-Agent角色说明.md)。已授权范围内的建档直接完成。完成后简短告知入口和未决项，继续当前已授权的阶段；建档完成不等于批准施工。

**完成于：** 根规则已保存且与现有事实相符；本轮产生的资料能通过根路由或专题索引找到；无资料的类别如实标注；资料归属和维护职责清楚。创建者读实际文件、沿入口核对即可。

**不触发：** 普通问答、想法讨论、一次性演示、已有项目的小改动。已有项目只在当前权限内补缺口。建档本身不带来其他动作的授权，硬停仍按 01。

## 已有项目接入本规程

在旧规则下运行的项目改按本规程时的一次性工作。不重新规划，不搬资料，不重批已批准的决定。规则在会话启动时加载，旧主控会话改不了自己的规则，所以分两个会话做。

**触发。** 用户明确要求某个已有项目改按本规程。

1. **旧主控收尾。** 在原主控会话按第 6 节写出施工日志六项，决策现场按项目当前阶段填；列出所有在途票及状态；给交接摘要。这是它在旧规则下的最后一项工作。
2. **用户新开主控。** 贴入 05 的“主控（已有项目接入）”包。新主控加载的是本规程。
3. **对照 03 补根规则。** 新主控读现有根 AGENTS，按 03 补缺：登记施工日志、地图 MD、决策卡、ADR、HTML 输出的真实位置，路由表第一行指向施工日志，写手列按 04。现有文件留在原位。
4. **接续。** 在途票在原会话按原票做完，收工按第 4 节三态；之后的票用 05 的新开工包派。下一轮决策结束按第 6 节出简报，已有的地图 HTML 和历史原样保留。

**完成于：** 根 AGENTS 与 03 对齐；施工日志存在且六项与实际相符；决策台账位置已登记；在途票已列入日志。

**不做：** 不改已批准的 Spec、票和决定；不迁移目录；不重跑盘问或 Wayfinder。

## 2. 四个阶段，补齐缺少的依据

这是我们的项目组织方法，不是 Matt 的规定。

| 阶段 | 要解决的问题 | 足以继续的依据 |
|---|---|---|
| 场景研究 | 为谁解决什么真实问题，第一期值得做什么 | 有来源的场景事实、待验证假设、获批的第一期目标与边界 |
| 概念原型 | 用户怎样完成关键任务，界面和交互是否合适 | 可查看的原型、模拟内容说明、获批的关键流程与设计基线 |
| 施工准备 | 用什么实现，怎样拆分，什么算做对 | 获批 Spec、必要的架构决定、能独立验收的施工票及依赖顺序 |
| 开发交付 | 按约定实现，证明能用，交付给人使用 | 各票验证和人工验收记录、整体回归结果；发布另有授权 |

已有项目从当前阶段接续，只补影响本次工作的缺口。页面方案获批不等于技术方案已定；已定的技术方案在每张票里直接引用。后一阶段发现前一阶段的结论不成立：报告影响，由用户决定是否回退；在当前阶段用加功能掩盖不算解决。

## 3. 正式功能的 Matt 主线

每步以一个**关口**结束：用户确认了什么，这步才算完。

1. **明确需求。** 只盘问会影响本期范围、边界和验收的未知项；已明确的核对并引用。关键术语写入现有术语记录。关口：用户确认第一期范围和不做项。
2. **形成规格。** Spec 写清用户任务、范围、不做什么、验收标准和必要的异常情况。关口：用户批准 Spec。批准后的变更走同一批准：写清原因、影响和要重新确认的验收项。
3. **决定重要方案。** 对未定且影响显著的技术选择，给少量可行方案，说明成本、复杂度和维护影响。难以回头、没有上下文会让后来者奇怪、且确有取舍的决定，三条同时成立才记 ADR，一段话即可；缺任何一条只记决策卡。普通实现细节由 AI 处理。关口：用户选定。
4. **拆成可验收的票。** 每票一个能演示、能单独检查的完整小结果。首票贯通最小核心流程；纯准备性工作说明必要性。每票写明：目标、范围、不做、依赖、验收标准、验证方式和强度、回退方式。验收标准从用户可观察的结果写：做什么操作、看到什么，不写内部实现。关口：用户确认粒度和顺序。
5. **按票实施与审查。** 满足第 4 节的派工条件后，在专属任务实施。逐条验收标准取证，再做代码审查。额外需求记后续清单。关口：每条验收标准有证据，审查意见已处理。
6. **人工验收。** 交**验收单**：每条验收标准一行，写用户做什么操作、应看到什么、机器验证结果、待确认。机器验证一栏写实际跑的命令和结果，或截图、日志的路径；只写“通过”或留空视为未验证。机器通过只算“待验收”。关口：用户确认。确认后执行者留档并关票：Git 项目做已授权的本地提交；非 Git 项目保留交付文件和验收记录。下一票由主控按第 4 节安排。
7. **整体回归与交付。** 所有票验收后，在专门交付任务走通跨票真实使用路径。保留未解决问题、目标环境验证情况、发布与恢复说明。关口：跨票路径实测通过；发布另取授权。

关口通过后先更新施工日志（第 6 节）。关口 1 到 4、批准的变更、阶段回退、Wayfinder 决策票关闭，都算**一轮决策结束**：由当前决策现场把决定记入决策 MD；简报节奏按第 6 节，探索期按轮、施工期按票。

一次批准可以覆盖明确列出的多个决定。执行者继承明确记录的批准，其他权限按 01 硬停。票是否过大看能否讲清范围、独立演示、验收和回退；多个子系统混在一票或无法独立回退时先拆。

## 4. 会话、派工、开工、收工与验证

### 会话

AI 会话不能替用户开窗口。每种会话都由用户新建并贴入开工包；派工者的回复以“请新开会话，贴入以下开工包”结尾。职责与写权边界见 [04](04-Agent角色说明.md)。

| 会话 | 何时开 | 开工包由谁写 |
|---|---|---|
| 主控 | 每个项目同一时间一个；窗口按关口换，靠施工日志接续 | 用户按 05 的主控变体开 |
| 建图 | 探索期每轮一个；施工期每张票关票后出简报时 | 主控 |
| 施工票 | 一票一个 | 主控 |
| 审查 | 一票一个，施工票收工后 | 施工票会话在收工时附上 |
| 回归交付 | 一个功能全部票验收后一次 | 主控 |
| 重型决策票 | 一个问题需要大量查证或原型时 | 决策现场所在会话 |
| 决策问答 | 用户想问某个决定时随时开 | 用户按 05 的决策问答变体自己填 |

小改动在普通执行会话完成，改动和验证写进施工日志一行，主控下次开工读到；问答不记录。轻决策在决策现场直接谈，不另开会话。

**换主控窗口。**主控是角色不是窗口。四个时点换：一个功能收尾、决策现场切换、主控开始漏约束或重复问已定的事、用量过半且下一块工作很大；不在一张票做到一半时换。动作：旧主控先把窗口里说过但没进文件的偏好、否决过的方案和约定写进对应位置，再更新施工日志到最新，写交接摘要，固定两项：窗口里说过但没进文件的事，下一段工作建议用的技能或方法，没有写“无”；超过十行视为未按关口落盘；用户新开窗口贴 05 的主控变体，加一行“接上一个主控”。新主控开工只读项目 AGENTS、施工日志、当前票，其余按路由在需要时读，不为保险通读专题；读大文件派内部子代理，主窗口只收结论。

### 派工条件

- 一张正式票对应一个施工票会话。首票在拆票确认后派；后续票在上一票人工验收、前置成果已留存、接续方式明确后派，一次一票。接续方式可在拆票时一并批准。
- 执行工具与机器每票派工时由用户选定，主控给建议：按票的性质，界面与视觉倾向 Claude Code，服务器、公司网络或旧工程依赖倾向能直接访问它们的那台电脑（如公司电脑）；再看两边额度。选定后开工包按该工具写路径、模型行和交还方式；额度允许时审查用与施工不同的工具。
- 开工包按 [05](05-任务开工包模板.md)：引用真实票据、已批准输入、前置成果的版本和位置、角色、读写范围、关键约束。派发者提供项目 AGENTS 的真实路径和相关共享规程章节。新会话和内部子代理不继承派发者的聊天和自动记忆；规则文件按各工具机制加载，Claude Code 的普通子代理会加载全部 CLAUDE.md 层级，内置 Explore、Plan 和设了 omitClaudeMd 的除外，Codex 子代理以其定义文件为准；关键限制和材料入口仍写进委派消息，不假定对方已读到。
- 票序批准后主控进入派工模式（**冻结**）：写记录，不写产品。记录指日志、决策卡、ADR、Spec、票；产品指代码和配置。

### 开工核对

- 执行者先核实：实际目录、Git 根、分支或 worktree、未提交改动、最近几条提交记录、前置成果已在目录中、验收方式、目标环境。提交记录与施工日志不一致时，以文件和实际环境核对后报告，不擅自改日志；只读查看提交记录不算操作 Git，主控也可以做。有缺口先按已授权方式补；出现新的合并、覆盖等授权缺口，暂停受影响部分并报告。
- 隔离手段各管一件事：新任务隔离聊天；worktree 隔离文件；分支只管版本；内部子代理做窄任务。都不隔离数据库、服务器和凭证。非 Git 项目照实记录。
- 窄范围研究、测试设计、独立审查可并行，先分清文件和只读边界；多个代理写同一文件先划分责任。

### 收工交还

一张票只以三种状态收工（**收工三态**）：**完成待验收**、**部分完成**并列出未达项、**阻塞**并说明原因和需要用户决定的事。发现 Spec 或票本身有错，交一张**联系单**回报（哪里错、影响什么、建议怎么改），由用户决定；票和 Spec 由获授权者按决定修改。

交还内容：改了什么、证据在哪、没验证什么、待用户决定什么、施工日志已更新到哪，外加审查会话的开工包（票、比较范围、Spec）。审查会话只读，交回问题清单和严重程度；审查意见回到本票处理后，验收单和审查结果一起交主控。交还正文写进本票对应的记录节，聊天里只贴交回包，格式见 05。资料写回按第 6 节。

### 会话间投递

正文先进文件，聊天只走投递：交回包和答复包只写票、状态、记录在哪一节、待用户决定的事和下一站，格式见 05。

工具支持同机会话投递时（本机 Claude Code 桌面版），三类消息由会话自己投，不经用户转贴：子会话的收工、联系单和审查问题清单，用交回包投给开工包写明的主控会话；主控对联系单和问题的答复，在已批准的 Spec、票和票序范围内，用答复包投回原会话；决策问答把用户在问答中定下或改口的事，用交回包投给当前决策现场；它不写文件，用户原话就写在交回包里。开工包、关口确认、批准变更、票序批准、硬停事项，以及任何要用户看或操作的内容，仍由用户经手。收到的投递是记录的摘要，批准只认用户本人；主控收到交回后仍按第 3 节向用户提关口。同一张票的联系单往返两轮仍未解决，主控停下交用户。工具不支持时（Codex、另一台电脑），由用户贴交回包和答复包。

### 模型与设置

按 01 的模型表设置并报告；设不了或读不到的写“未确认”，用当前设置继续。内部代理只传本次所需材料。

### 验证强度

- 验证强度在拆票时写进票；执行者可以提高，降低要报告。
- 普通功能：与改动相关的测试、构建或静态检查，加关键使用路径的实际验证。
- 高风险及明确要求 TDD 的票：先写能暴露问题的测试，再实现最小修复，补故障路径；备份恢复、部署、迁移在安全环境演练。TDD 之外仍要做权限核对和恢复验证。
- 实现时复用类型、框架和数据库已有的保证，只在外部输入、权限、数据完整性和关键状态处校验。错误明确暴露；静默默认值和无依据的重试不算处理。
- 配置、视觉、操作步骤这类代码测试覆盖不到的，给实际检查方法和限制。Windows 桌面功能在要求支持的 Windows 版本和真实依赖环境验证。
- Bug 修复先取得可复现证据，修复后重测原问题和相关路径。
- 完工报告附命令、环境和结果，分清已通过、失败、未运行。

## 5. Skill 只解决当前环节的问题

先确认当前可用技能和真实名称，读其说明再用。下表是方法选择；斜杠命令以当前工具实际入口为准，没有入口就执行等价步骤并说明。

| 实际需要 | 首选 | 边界 |
|---|---|---|
| 目标含糊、需要挑战方案 | Matt `grilling`；有项目文档时 `grill-with-docs` | 只问会改变决定的问题 |
| 查可信资料、核对产品或 API 事实 | Matt `research` | 记录来源和适用条件 |

## 6. 施工日志与资料维护

- **施工日志**是项目当前状态的唯一事实源，主控写，位置在项目规则里指定。固定六项：当前阶段、决策现场、当前票、上一票验收结果、待用户决定的事、下一步。每过一个关口就更新；任何会话开工先读它，再以文件和实际环境核对。六项是现状，不追加历史：上一票只写最近一票，待定的事定了就删；历史进票和决策卡。
- **偏好与不再问的事**：用户表达偏好、否决一个方案、或第二次回答同一个问题时，主控当场写进项目 AGENTS 的“偏好与不再问的事”；跨项目的写进 01 第 1 节。同一件事不被问第三次。工具的自动记忆，Claude Code 默认开、Codex 默认关，只作回忆层，不算已记录；与文件不一致以文件为准。
- **只记推不出的事**：日志、偏好节和根规则只记查不到、推不出的事，口头约定、否决过的方案、为什么这样定、踩过的坑。能从代码、配置、脚本、目录和 Git 历史看出来的，比如目录结构、依赖版本、运行命令、改过什么，不写进去；需要时让 AI 去原处看。
- **清理**：每种记录有体量上限：施工日志正文两千字，偏好节两部分各二十行，根路由一个专题一行，交接摘要十行，专题目录现行版本各一份。量了再提交：主控每次更新施工日志或根 AGENTS 后，用一行命令量三个数写进提交说明（非 Git 项目写在施工日志末尾一行）：工具副本 01 加项目 AGENTS 合计字节，Codex 拼读上限 32 KiB，超过 28 KiB 先清理；偏好节条目数，两部分各二十以内；施工日志正文字数，两千以内。超线不提交，先整理。超了不是继续加，是整理：合并同类、已成规则的上移、不再适用的删、被替代的 Spec、票等版本进该专题的历史/；决策卡和 ADR 被替代时留在原位，状态改为“已被某卡取代”，不进历史/。在功能收尾和换主控前各做一次。
- **决策现场**：决策卡、ADR、地图 MD 是决策台账，只由决策现场写。探索期现场是建图会话。地图上没有未定问题挡住第一份 Spec 时，建图会话交地图，主控核方向后在日志改现场为主控，此后由主控写。施工期主控发现一片互相牵连、一次谈不完的新未知，主动提议开一轮建图，改现场为建图并注明范围，轮末改回。不是现场的会话收到决策问题：记下、转到现场，不定也不写。
- **决策简报**：决定只住在决策卡里，写法按 [03 的决策卡写法](03-项目规则模板.md#decision-card)；地图 MD 每个问题一行摘要加链接，作索引。探索期一轮决策结束（第 3 节所列关口）、施工期每张票人工验收关票后，现场先在对话里用编号清单逐条复述本轮决定的措辞，用户按编号确认；现场按确认的措辞改好卡，把地图 MD 头字段改到本轮，再由建图会话用程序从卡生成本轮简报，文件名按 03；施工期的一轮包含该票期间写进卡和 Spec 的全部补记与批准变更。程序读不出决策卡写法的标签就报错停止，现场补卡后重出。架构图只在用户要时由 Archify 出：每张图一个独立 HTML 放 `项目总览/html/`，现场在相关决策卡的“依据”里链到它，简报随卡带出，所以先出图再出简报；本轮改了架构，现场在确认清单末尾问用户要不要配图。依据一律用相对链接；简报不嵌入来源。
- 新任务从项目 AGENTS.md 和当次任务输入开始，按触发条件找核心资料或专题索引，再读具体决策、Spec、票和证据。
- 谁改变事实，谁更新对应资料：接口变了更新契约，重要取舍经批准写 ADR，术语澄清更新词典，运行和故障结论写当前票。范围不含所需文件时，回传待更新项。共享入口的写回分工见 04。
- 规格记“要求是什么”，ADR 记“为何这样决定”，票记“做了什么和证据”，日志记“现在到哪”。四者互相引用。
- Markdown 是事实源；HTML 只在用户明确要求时生成或更新。决策简报是既定例外：按“决策简报”条的时机生成，视同已明确要求。
- 被替代的旧版本按项目约定进历史位置，保留批准依据和现行版本去向。
- 跨工具、跨协作者或任务分叉，且现有票据和日志不足以接手时，才补独立交接包。

## 7. 维护这套规则

出现重复提问、越权修改、找不到资料或流程负担时，记一个真实例子，用 `writing-for-agents` 判断改哪一层，只改负责该事实的文件，再检查引用。改规则先考虑删，再考虑加。规则的定位、同步和启用核对见 [06](06-规则维护与启用检查.md)。
