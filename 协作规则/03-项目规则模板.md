# 项目规则模板

> 正式模板：2026-09-27（修订）。用于生成项目根 AGENTS.md。何时建档、由谁建、做到什么算完成，见 [02 新项目启动与最少建档](02-通用开发规程.md#project-startup)。

## 使用前

- `[方括号]` 是待核实的占位符，不是事实、路径或命令。
- 逐项核实；不适用写“不适用＋理由”，未确认写“待确认”。
- 路径指向真实文件。已有合适的目录和文件沿用，不为套模板搬迁。
- 根 AGENTS.md 是唯一项目规则正文。CLAUDE.md 如需接入，作为工具入口引用它，接法见 [06](06-规则维护与启用检查.md)。
- 体量：01 加项目 AGENTS 合计保持在 32 KiB 以内，数字和原因见 06 的接入说明；每行一个专题、不超过二百字，长段落下沉到项目文档留一行指针；量法和清理线见 02 第 6 节。
- 全文只写现行事实，不写日期、提交号、经过和原话；变化经过在票、决策卡、Spec 变更记录和 Git 历史，需要时去原处看。

## 项目资料目录

新项目按下表建立；目录随实际内容建立，不预建空目录。已有项目沿用现有位置，在下一节登记真实路径。

| 位置 | 内容 | 写手 |
|---|---|---|
| `AGENTS.md` | 唯一项目规则正文，含下方路由 | 主控 |
| `README.md` | 项目介绍和人类阅读入口，不维护进度 | 主控 |
| `项目总览/md/施工日志.md` | 项目当前状态的唯一事实源，六项：当前阶段、决策现场、当前票、上一票验收结果、待用户决定的事、下一步 | 主控 |
| `项目总览/md/总览.md` | 项目总览页“功能与架构”标签的源：开头是头字段“现状”“核对”，之后是介绍段、按五段骨架分组的功能清单、技术架构；写法见下文“总览 MD 头字段与分组” | 主控，关票后与架构变动后更新，改完当场出页 |
| `项目总览/md/决策地图.md` | 决策台账，也是项目总览页“每轮决策”标签的源：开头是头字段，之后每个问题一行索引，再接各轮批准段；写法见下文“地图 MD 头字段与批准段” | 决策现场；批准段里“定了要做”的进度由主控在关票时改 |
| `项目总览/md/adr/` | 难以回头的决定，各一页；项目已有 ADR 目录则沿用 | 决策现场 |
| `项目总览/md/` 其余 | 架构、术语等跨专题资料 | 主控 |
| `项目总览/html/总览.html` | 用户看的那一页，两个标签“功能与架构”“每轮决策”，由项目总览生成器从总览 MD 和地图 MD 生成，不手改；旧的简报和地图 HTML 原样留在同目录作历史 | 谁改了源 MD 谁当场出页：主控；探索期轮末是建图 |
| `专题工作/某专题/决策卡/` | 该专题每个问题一张卡；写法和状态五值见共享规程 03“决策卡写法” | 决策现场 |
| `专题工作/某专题/` 其余 | 策划书、Spec、施工票、验收记录和证据，专题索引 | Spec 和票由主控写；票的记录和索引由执行者写 |
| 所属目录的 `历史/` | 被替代的 Spec、票等旧版本，保留批准依据和现行版本去向；决策卡和 ADR 不进历史，原位改状态 | 替换它的写手 |

MD 是事实源，HTML 是阅读副本。有效决定和已完成的票留在所属专题，完成不等于进历史。

## 决策卡写法

本节是各项目共用的写法：生成项目 AGENTS 时不抄进去，项目里写卡和地图 MD 直接按本节。

每张卡一个文件，`专题工作/<专题>/决策卡/NN-名称.md`。开头是固定标签，一行一项，冒号用中文全角；正文是固定标题的段落。程序按标签和标题读，缺标签报错；某项没有内容写“无”，不留空。

```text
# 决定：[结论句，作标题；未定时写“未定：问题一句”]

状态：[未定 / 已定 / 否决 / 暂缓 / 已被某卡取代]
定于：[日期；未定写“无”]
谁定的：[人；按 01 第 2 节由 AI 代定的写“AI 代定，可改”；未定写“无”]
出处：[批准原话所在的文件与位置；未定写“无”]
依赖：[前置卡名称与相对链接，一行一个；无则“无”]
取代：[本卡取代的卡名称与链接；无则“无”。旧卡的状态行同时改为“已被某卡取代”并链到本卡]
影响哪些卡：[本卡改动会牵动的卡名称与链接；无则“无”]

## 给你的三句话
[像建筑里的什么；选了什么；你用起来会有什么不同。第四行写你要做的一个动作，没有写“无”。用白话，术语第一次出现时解释]

## 问题
[一两句背景，用用户的语言]

## 比较过的选项
| 做法 | 好处 | 代价与风险 | 排除理由 |
|---|---|---|---|

## 选择与理由
[选了什么；再以“为什么更好：”起头写一行，项目总览页取这一行]

## 影响
[接受的代价；对成本、进度、使用、维护和其他决定的影响；改了旧决定时另起一行写改动，写法见下]

## 前提
| 前提 | 谁负责满足 | 何时核实 | 不满足怎么办 |
|---|---|---|---|

## 依据
[可点开的相对链接，一行一个：查证记录、ADR、原型、讨论记录]

## 后续
[谁＋做什么＋何时之前，一行一个；无则“无”]

## 暂缓原因
[状态为暂缓时必填：为什么不定、重新考虑的触发条件；其他状态写“无”]
```

标题写决定本身，不写问题；人读文字用名称，不用裸编号；文件名、链接、状态行里的卡号不算裸编号，ADR 编号也不算。

- 给你的三句话：新写的卡、改定的卡、写进批准段时引用到的卡，这一节都写实，不用“无”代替；更早的卡不回填。项目总览页“为什么这样定”取这一节加“选择与理由”里“为什么更好：”起头的那一行；卡里没有这一节就不出这一格。
- 出处：在对话里按选项确认的决定，选项题和答案按 02 第 6 节存进项目后，出处指向那里；原话只在对话里、没存进项目的，出处写“见本卡”，并在“选择与理由”里逐字留下所选的选项。
- 比较过的选项：原记录里没有的格写“未记录”；原记录没单列排除理由时，可以按这个做法的代价归纳，以“按代价归纳：”开头。
- 影响：改了旧决定（卡、ADR 或其他已批准的约定）时另起一行，整行按“原值 → 本次 → 新值”写，三段、两个“→”；程序只认这样的整行，说明文字里要用箭头就放在引号里。再次改定时删掉以前各轮的改动行，只留本次；同一次改动涉及两张卡时，只在一张卡写改动行，另一张写一句指向。
- 前提与后续：决定成立所依赖的条件写“前提”；决定成立后要做的事写“后续”。
- 拆卡：一张卡含多项决定时拆成多张，拆出的卡“依赖”写原卡；原来依赖原卡的卡，按依赖的内容改指相应的卡；拆卡不写“取代”。

研究卡（只查证不决定）用同一写法：状态写“未定”，查证完成写“已定”，被取代时同其他卡；查证完成后，“定于”写完成日期，“谁定的”写实际做查证的会话或人，“出处”写查证记录的链接，查证就写在本卡里时写“查证记录即本卡”；“比较过的选项”写“无”；结论放“查证结论”段，代替“选择与理由”。

### 地图 MD 头字段与批准段

`项目总览/md/决策地图.md` 开头固定四个标签，之后才是每个问题一行的索引：

```text
轮次：[第 N 轮；日期]
本轮范围：[一句]
要用户决定：[没有写“无”；有的每项一行：问题一句；选项一行一个含“什么都不做”，各附代价；推荐及理由；何时之前；不定会挡住什么]
下一步：[谁＋做什么＋何时之前，一行一个]
```

有多项的标签（要用户决定、下一步）：标签行之后接着写，到下一个标签为止，中间可以空行；每项一行、不缩进，写不写列表符号都行；一项的子项（选项、推荐、何时之前、会挡住什么）缩进两格写在该项下面。

“要用户决定”就是项目总览页两个标签上方的横幅“现在要你定的事”；“下一步”是台账里接下来谁做什么，决策问答和施工日志对照用，不上页；页面每轮末尾的“接下来”取该轮批准段的“接下来：”一句。四个标签之后直接接索引，别的说明写成 HTML 注释，否则会被当成上一个标签的续行。改了头字段或批准段就当场出页。

索引行写法同上：每个问题一行，问题、依赖、状态和一句摘要加链接，不复述卡的内容。各轮的批准段接在索引之后，一轮一段，写用户按编号确认过的白话，固定结构：

```text
## 第 N 轮 · YYYY-MM-DD · [主题一句]
定了要做：
- [一句白话，同事用起来会怎样] ｜ 进度：[已完成／进行中／待完成] <!-- NN 卡 -->
定了不做 / 以后再说：
- [一句白话，为什么] <!-- NN 卡 -->
还没定：
- [一句白话，等什么]
比较过、没选的做法：
- [一句白话，没选的原因]
接下来：[一句，谁在何时之前做什么]
```

四个清单没有内容的写“无”。正文不出现卡号、票号，出处只在行尾 HTML 注释里：“定了要做”“定了不做 / 以后再说”每条行尾注释写决定所在的卡，写法 `<!-- NN 卡 -->`，要带票号写 `<!-- NN 卡；票 NN -->`，生成器按卡号打开卡取“为什么这样定”；“定了要做”的进度由主控在关票时改。旧写法的批准段原样留着，生成器只读这种结构的轮次。

### 总览 MD 头字段与分组

`项目总览/md/总览.md` 全文三屏左右：开头固定两个标签，之后是介绍段、功能清单、技术架构。

```text
# [项目名] 功能与架构总览

现状：[一句话，40 字以内，写到哪一步]
核对：[YYYY-MM-DD，最近一次核对全文的日期]
```

- 标题是项目名加“功能与架构总览”，页面标题由生成器取项目名；“现状”出在页面标题下，“核对”出在元信息行。
- 介绍段两三段白话：平台做什么、给谁用。到哪一步写在“现状”里；五种状态的说明由页面图例表达，介绍段不写。
- 功能清单按五段骨架分组：进入（装、申请、登录、从平台进来）→ 使用（使用者日常做的事，按一次典型使用的先后，可拆几组）→ 管理（管理员做的事）→ 维护（更新、反馈、备份恢复）→ 后台（服务器、部署、加密等使用者看不见的部分）。三级标题写“段名：组名”；段名只用这五个、按此顺序出现，没有的段不写；组名用使用者的话写具体，不用技术名；一组 4 到 12 项，超了拆、少了并；一个功能只进一组；全部不超过 10 组。生成器校验段名、顺序、组数和每组项数，不合格报错不出页。
- 功能一行一个，三栏：功能（白话写同事或管理员能做什么）、状态（✅ 用户亲手验收过／进行中／待完成／未定／不做，只认这五个写法）、还差什么或为什么（非 ✅ 必写）。
- 技术架构一节一块一行：管什么、用的技术加一句白话、像建筑里的什么；末尾一两句串一遍同事点开一个模块经过哪几块；不配图。
- 正文不出现票号、卡号、需求编号、版本号，出处写在行尾 HTML 注释里；完成情况的数字由生成器算，不手填。
